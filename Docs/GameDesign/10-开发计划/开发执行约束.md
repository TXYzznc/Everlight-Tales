# 开发执行约束

生效日期：2026-09-20。本文件约束《第一版开发任务表》的使用方式与后续 OpenSpec 的建立规则；结构参照《星际拓荒：自动纪元》开发计划模板，按本项目（纯 2D 移动端、AI-Friendly-Project 框架基线）适配。

## 第一版开发任务表所有权

- `第一版开发任务表.xlsx` 是第一版任务顺序、依赖、里程碑、工时区间和状态的用户维护来源。
- 只有用户本人可以修改该工作簿。AI、Agent、SKILL、脚本和自动化工具始终只有只读权限，不得因用户授权开发、文档维护或其他项目工作而取得写入权限。
- AI 不得直接或间接编辑、覆盖、另存后替换、重算后回写该工作簿，也不得修改其中的状态、实际工时、依赖和备注。
- 开发过程产生的状态、工时、依赖或备注调整只能作为建议列出，由用户决定是否手动更新原工作簿。
- 禁止创建并行的权威副本；任务 ID、顺序、依赖、阶段验收门和状态始终以用户维护的原工作簿为准。

## 与 OpenSpec 的职责边界

- 开发任务表决定任务顺序、前置依赖和阶段验收门。
- `Docs/GameDesign/` 提供产品与系统设计依据；`Docs/Framework/Development/` 提供框架与协作规范。
- OpenSpec 负责单个或一组相关开发任务的需求、方案、可测试场景和实现任务分解。
- 代码、数据、资源与测试负责实现和验证；不得反向覆盖开发任务表。

## OpenSpec 分组与命名规范

- 一个 OpenSpec 原则上对应开发任务表中的 2～5 个任务，由 AI 根据任务目标、依赖关系、实现内聚性和可验收边界自行决定具体数量；不得机械地一项任务建立一个 OpenSpec，也不得把整张任务表一次性纳入同一个 OpenSpec。
- 同一个 OpenSpec 内的任务必须目标一致、依赖连续，并能形成共同的设计与验收边界；即使任务属于同一模块，也不得跨越阶段验收门组合。
- OpenSpec change ID 同时作为目录名和文档中的变更名称，必须使用 OpenSpec CLI 兼容的英文 `kebab-case`：仅使用小写英文字母、数字和连字符，不使用中文、空格或下划线。
- OpenSpec change ID 必须包含以字母 `b` 开头的批次号、对应任务编号和简短英文任务概要。批次号格式为 `b<两位序号>`；任务编号允许简写并转为小写，但必须能够无歧义地映射回任务表中的原始任务 ID。
- 非并行 OpenSpec 命名格式：`b<两位序号>-<任务编号范围或组合>-<英文任务概要>`，例如：`b01-p01-p03-engineering-baseline`。
- 同一执行批次存在并行 OpenSpec 时，共用相同的管理批次号，并在批次号后标记 `parallel` 和并行领域；命名格式为：`b<两位序号>-parallel-<领域>-<任务编号范围或组合>-<英文任务概要>`，例如：`b07-parallel-program-p101-p103-day-loop`、`b07-parallel-art-art011-art013-ui-visual`。
- 管理批次号按执行批次递增；同批并行项复用批次号，下一批使用下一个序号。
- 建立 OpenSpec 前必须对照任务表核验原始任务 ID、前置依赖和阶段验收门；OpenSpec 的 proposal、design、specs 与 tasks 必须明确列出其覆盖的原始任务 ID，名称中的简写不得替代正文中的完整 ID。
- 后续所有 OpenSpec 的规划、创建、实施、验证与归档都必须遵守本节；若实际开发发现任务分组需要调整，只能调整 OpenSpec 边界或向用户建议修改任务表，不得由 AI 擅自修改任务表。

## OpenSpec 方案确认门禁

- 开发任务表和 `Docs/GameDesign/` 确认的是需求、范围、顺序与验收依据，不代表具体实现方式、技术架构或美术生产方案已经获得确认。
- 每个 OpenSpec 在创建或填写 artifact 前，必须先与用户讨论该变更的实现方式和大方向设计；不得把需求已确认推定为实现方案已确认。
- 必须讨论并取得用户确认的内容包括：模块与程序集边界、数据模型、公共接口、生命周期、依赖关系、资源结构、序列化与存档语义、异步与取消、性能约束，以及会影响后续工作的工具或生产流程。
- 局部代码写法、私有成员命名、等价重构和不改变已确认契约的机械实现细节可由 AI 自行决定，但仍须遵守项目约定和对应 OpenSpec。
- 讨论完成后，AI 必须先提交该 OpenSpec 的决策摘要，至少包含目标、选择的方案、明确边界、验收方式和约束。只有用户明确确认该决策摘要后，AI 才可以创建或填写 proposal、design、specs 和 tasks。
- 并行 OpenSpec 分别执行方案确认门禁；同一批次编号不构成共享授权。
- 实施中若发现需要改变已确认的架构或实现契约，必须暂停相关实现，重新与用户讨论并取得确认，再更新 OpenSpec；不得先实现后补写方案。

## 方案讨论增量归档

- 连续方案讨论每累计两轮，必须至少完成一次增量归档；重大边界、不可逆选择或会影响后续任务的结论确认后立即归档。
- 已确认的设计决定写入[设计决定](../07-设计参考/设计决定.md)（沿用 D-xxx 编号）；当前完成度同步到[设计状态](../07-设计参考/设计状态.md)，未决事项同步到[待完善设计](../07-设计参考/待完善设计.md)。
- 增量归档不等于 OpenSpec 最终决策摘要，也不构成 artifact 创建授权。

## 美术与音频并行路线

- 本作为纯 2D 移动端：美术路线包含 UI 视觉与图标、立绘与状态差分、场景背景、盘面零件／设施图与 2D 动效、音效与音乐；不涉及 3D 建模管线与独立美术工程。
- 美术任务先完成视觉规范与代表性样张（ART0），再批量制作（ART1），最后按领域分批导入主工程验收（ART2）。
- 程序灰盒不等待正式美术；立绘、背景、音效按"有限素材"口径先行，只有最终第一版验收（G6）要求 ART2 完成。
- 音画素材范围以[音画与文本素材清单](../07-设计参考/音画与文本素材清单.md)为准，逐节点台词按系统定稿后分批补齐（D-076）。

## 多窗口职能协作与任务派发

- 多窗口并行协作统一从[多窗口任务派发](../../Framework/Development/Dispatch/README.md)进入；固定窗口注册与自动派发见[固定窗口注册与自动派发](../../Framework/Development/Dispatch/WindowAutomation.md)。未经用户明确要求不得自动创建新的用户可见窗口。
- 制作人窗口负责只读核对任务表、拆分批次、生成派发单、检查跨职能依赖和冲突、组织联合验收及 OpenSpec 归档；默认不替代专业窗口决定具体实现细节。
- OpenSpec 建立前，派发单位于 `Docs/Framework/Development/Dispatch/Active/`；OpenSpec 建立后派发单随对应 change 归档。
- 同一业务目录在同一时段只能有一个实现窗口拥有写权限；同一 Unity 工程不得由两个窗口同时驱动。Unity Skills 固定映射主工程 `Everlight-Tales` 使用 8090 起端口；固定端口不替代项目身份核验。
- 多窗口共享同一 Git 工作区时必须把 Git 索引视为短期独占资源；专业窗口禁止 `git add -A` 或 `git add .`，只能显式暂存派发范围路径。
- 专业窗口必须返回提交号、修改范围、验证证据、已知限制和未决事项；所有窗口只提交、不推送，提交说明使用中文。
- 依赖变化、设计冲突、紧急缺陷和工作转交统一遵守[暂停、抢占与恢复协议](../../Framework/Development/Dispatch/PauseAndRecovery.md)；抢占严重度 S0～S2 不与任务表 P0／P1 优先级混用。

## 项目框架约束（与 AGENTS.md 一致）

- 产品业务不得进入 `Assets/Game/ScriptsBuiltin/`；框架纯度审计通过是每个阶段验收门的固定项。
- 输入必须经过项目 InputModule 抽象，不得直接读取 `UnityEngine.Input`。
- 不把 ScriptableObject 当运行时数据库；配置走 DataTable／Config 加载链。
- Editor Play Mode 内的小范围 C# 方法体迭代可用 FSR；结构变更必须停止 Play Mode 按普通编译流程验证。
