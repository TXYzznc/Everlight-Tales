## Context

b01 已建立五层业务程序集（`Data` / `Board` / `Meta` / `Events` / `UI`），其中 `Board` **零引擎依赖**、`Meta` 已引用 `Builtin.Runtime`。本批次四项任务全部落在 `Meta` 与 `Board` 内。

框架侧已具备的设施（已实地清点，非假设）：

| 设施 | 位置 | 对本批次的意义 |
|---|---|---|
| `NewtonsoftJsonHelper` | `Assets/Game/ScriptsBuiltin/Runtime/GFHelper/` | 序列化直接复用，不引入新依赖 |
| `DefaultJsonHelper` | `Assets/Plugins/UnityGameFramework/Scripts/Runtime/Utility/` | 框架 JSON 工具的接口实现 |
| `DefaultSettingHelper` | 同上 | **GF 自身的落盘范式**：`Path.Combine(Application.persistentDataPath, SettingFileName)` + JSON |
| `GFDiagnosticScenario` / `GFDiagnosticReport` / `GFDiagnosticSnapshot` | `Assets/Game/ScriptsBuiltin/Runtime/Diagnostics/` | 诊断以"场景（scenario）产出报告"的模式组织，可直接沿用 |
| `Utility.Path` | 框架 Utility | 跨平台路径归一化 |

因此本批次**不引入任何新第三方依赖**，序列化与落盘全部沿用框架既有约定。

## Goals / Non-Goals

**Goals**

- 双存档（世界／尝试）可读可写可往返，带独立版本号，版本不符时行为确定。
- 随机源提供统一入口，同种子产出同序列，随机消费次数可查询。
- 四类配置表的字段草案落文档，字段归属到具体任务。
- 诊断接入框架既有模式；演算日志可开关，开关状态下的演算记录可复现。
- `Board` 的零引擎约束不被破坏。

**Non-Goals**

- 不实现任何具体存档内容（世界状态字段、尝试盘面数据）——那些由 `G2`/`G3` 的任务定义。
- 不实现存档加密、压缩、云同步、多存档槽位。
- 不实现随机数算法的统计质量评估（本批次只保证确定性与可计数）。
- 不冻结配置表的最终字段（`P0-011` 只登记草案；最终冻结随各表归属任务推进）。
- 不实现盘面演算本身（`G1` 起）。

## Decisions

### D1：世界存档与尝试存档为两个独立文件

| 存档 | 文件 | 内容性质 | 写入时机 |
|---|---|---|---|
| 世界存档 | `Save/world.json` | 跨局持久的进度（`G3` 起定义字段） | 由世界状态变更点触发（`G3` 定义） |
| 尝试存档 | `Save/attempt.json` | 单次维修尝试的进行状态（`G2` 起定义字段） | 轮间四选一之后写入，中断后按轮恢复（`P2-010` 定义） |

两个文件**各自带版本号**，互不阻塞：尝试存档损坏不应导致世界进度不可读，反之亦然。

选择理由：任务说明原文即为"世界存档＋尝试存档**双文件**"。分开存放让"尝试存档被频繁覆写"与"世界存档低频且关键"两种生命周期互不干扰——尝试存档是高频覆写且可丢弃的，世界存档是低频且必须可靠的。合成单文件会让高频覆写威胁到世界进度。

替代方案「单文件 + 分节」被放弃：一次写入失败会同时损坏两类数据，且无法对尝试存档单独采用"损坏即丢弃重开本轮"的策略。

### D2：序列化复用框架 JSON，不引入新依赖；不加密

用 `NewtonsoftJsonHelper`（框架已带）序列化，落盘沿用 `DefaultSettingHelper` 的范式：`Path.Combine(Application.persistentDataPath, "Save", <name>.json)`。

存档结构统一为三段信封：

```
{ "version": <int>, "savedAtUtc": <string>, "payload": <object> }
```

**不加密、不压缩**。理由：单人离线项目，本地存档的价值密度不足以抵御有意篡改，而加密会引入密钥管理这一额外失败面；任务说明也未要求。若后续需要，信封的 `version` 字段已为升级留出入口。

**版本不符的处理策略**：`version` 高于当前支持版本 → 拒绝读取并明确报错（不静默降级）；低于当前 → 留出迁移钩子，本批次仅实现"记录并拒绝"，迁移在真正需要时补。

### D3：随机源采用"固定种子为主、可插拔来源"的结构

```
ISeedSource          // 提供本次使用的种子
  ├─ FixedSeedSource  // 关卡固定种子（默认，保证可复现）
  └─ MixedSeedSource  // 固定种子 + 随机混合（P2-009 的"固定/随机按元素指定"）

RandomService
  - NextInt(min, maxExclusive)
  - NextFloat()
  - ConsumedCount      // 随机消费次数，只增不减
  - Reset(seed)        // 重置种子并清零计数
```

关键点：**消费计数在服务内部集中记账**，而不是让调用方各自统计。`P1-012` 的同种子复现与 `P2-017` 的批量演算校准都能直接读 `ConsumedCount` 判断两次演算是否走了同一路径。

业务代码**禁止**直接调用 `UnityEngine.Random` 与 `System.Random`；全部经 `RandomService`。这是一条与 b01 输入抽象同构的边界约束，可用静态扫描验证。

### D4：随机源放在 `Board` 还是 `Meta`

放 **`Board`**。

理由：随机消费发生在盘面演算内部（初盘生成、事件抽取），而 `P1-012` 要求"同种子复现"必须在**无引擎环境**可验证（b01 已确立 `Board` 零引擎正是为此）。若随机源放在 `Meta`，盘面演算就被迫依赖带引擎的程序集，b01 刻意建立的离线演算能力会被破坏。

代价：随机源的接口必须是零引擎的（只用 `System` 与基础类型），不能出现 `UnityEngine.Vector2` 之类。这与 b01 对 `Board` 的既有约束一致。

### D5：配置字段草案的登记口径与归属

`P0-011` 的 DoD 是"首批字段清单落文档"，且任务说明列了**四类表**：事件模板／关卡／零件／Buff。登记策略：

| 表 | 草案字段来源 | 最终归属 |
|---|---|---|
| 事件模板 | 事件触发条件、权重、效果引用、文本引用 | `G1` 事件任务 |
| 关卡 | 盘面半径、轮数、拍数、目标分、特殊效果目标、携带上限 | **`P1-021`（关卡盘面配置表）** |
| 零件 | 类型、能力引用、能量消耗、附着规则 | `P1-007`／`P1-008` |
| Buff | 类型、叠加规则、持续时间、触发时机 | `P1-018`／`P2-005` |

**本批次只登记草案并标注归属任务，不宣称冻结**。理由：任务表的 `P0-011` 与 `P1-021`（关卡盘面配置表，属于 G1）存在真实的口径重叠，硬在本批次"冻结"关卡字段会与 `P1-021` 冲突。登记草案 + 显式标注归属，既满足 DoD 又不制造与下游任务的矛盾。

登记落点：`Docs/GameDesign/07-设计参考/` 下的字段草案文档，**写入现有设计口径文档体系**，不新建与任务表并行的权威副本。

### D6：诊断沿用框架的 scenario 模式；演算日志开关归属 `Board`

诊断侧复用框架既有的 `GFDiagnosticScenario` → `GFDiagnosticReport` 模式，新增一个业务诊断场景（产出表加载状态、程序集布局、随机消费计数等摘要），而不是自建一套诊断框架。

演算日志开关放在 **`Board`**（`BoardLog` 之类的静态开关 + 记录缓冲），原因同 D4：演算发生在 `Board` 内且必须能在无引擎环境复现；诊断场景（`Meta` 侧）只是把 `Board` 的记录汇入框架报告。

日志开关的语义：关闭时零开销（不做字符串拼接、不分配）；开启时记录**可复现的演算步骤**（种子、初始盘面、每步动作与随机消费数），使"同一份日志能重放出同一结果"成为可验证断言。

## Risks / Trade-offs

- **风险**：存档格式被 `G2`／`G3` 大量读写点依赖后才发现字段不够，导致全量迁移。→ **对策**：三段信封预留 `version`；本批次只定"容器与时机"，字段留给各归属任务；`payload` 用对象而非扁平字段，允许按需增删。
- **风险**：随机源放在 `Board` 后，有人为了让盘面用上 `UnityEngine.Random` 的便利而破坏零引擎约束。→ **对策**：`noEngineReferences: true` 让引擎类型在编译期不可用；批次验证固定跑 `verify_project_assemblies.py` 与该程序集的零引擎检查。
- **风险**：静态扫描"禁止直读 `UnityEngine.Random`"可能出现漏网（例如经中间封装绕过）。→ **对策**：扫描作为**回归护栏**而非唯一保障；主要保障是 `Board` 的编译期零引擎约束与 `RandomService` 作为唯一入口的代码评审。
- **风险**：`P0-011` 与 `P1-021` 的口径重叠被后人误读为"G0 已冻结关卡字段"。→ **对策**：草案文档在表格内显式标注每类字段的最终归属任务，并在文档开头写明"草案，非冻结"。
- **风险**：诊断接入与演算日志开启后自身成为性能开销（高频循环分配）。→ **对策**：开关关闭时零开销；开启时日志写入预分配缓冲，不在每步拼接字符串（遵循框架"不在高频循环制造 GC 分配"的约定）。
- **权衡**：`P0-011` 在本批次只能登记草案，DoD 的"首批字段清单落文档"达成，但字段稳定性弱于任务表字面。这是与 `P1-021` 共存的必要妥协，已显式记录。

## Migration Plan

无迁移：四项均为业务侧新增。回滚方式为删除 `Meta/` 与 `Board/` 下的新增文件、删除持久化目录下的存档文件（运行时产物，不在版本库内）。
